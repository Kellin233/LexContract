## 📖 项目背景

合同与法律协议通常篇幅长、结构复杂，一个问题往往需要结合多个章节甚至多份文档才能判断。直接使用大模型处理这类任务，主要面临三个问题：

- **条款分散：** 相关定义、义务、例外和补充约定可能位于不同章节，单次检索难以找全。
- **结论难验证：** 模型可以生成看似合理的回答，但引用可能不完整、脱离上下文或无法回到原文。
- **复杂问题难覆盖：** 涉及多方权利义务、交叉引用和冲突条款时，需要持续检查证据缺口并补充调查。

LexTrace 面向这些问题，构建了一套以合同原文为基础的多 Agent 审查链路。系统不仅回答问题，还保留结论所依据的完整条款及其位置，使审查结果能够被复核和追溯。

## 🎯 设计目标

> 让 Agent 不只是“读完合同后给出回答”，而是先明确需要调查什么，再逐条收集和验证证据，最后基于可信原文形成结论。

- **拆解复杂问题：** 将跨章节问题转化为可以独立取证的调查要点。
- **覆盖关键条款：** 结合语义检索和精确匹配，从不同表述中定位相关内容。
- **保证证据真实：** 引用必须来自合同原文，并通过程序校验。
- **输出可复核结论：** 报告中的判断、证据和待确认事项保持清晰关联。

## 💡 解决方案

| 环节 | 职责 | 设计方式 |
| --- | --- | --- |
| **规划 Agent（Planner）** | 拆解合同问题 | 将原问题转化为多个调查要点，只定义“查什么” |
| **搜索 Agent（Searcher）** | 并行查找证据 | 通过工具调用完成混合检索、精确定位和原文展开 |
| **报告 Agent（Refiner）** | 生成最终结论 | 只读取已校验证据，输出结论、分点分析和引用 |
| **证据层** | 保存和共享可信原文 | 完整条款物化、程序校验、位置去重和编号索引 |

**整体链路**

```text
用户问题
    ↓
Planner 拆分调查要点
    ↓
多个 Searcher 并行取证
    ↓
恢复完整条款并校验原文
    ↓
Refiner 基于已校验证据生成审查报告
```

## ✨ 项目亮点

**可控的多 Agent 编排**

系统使用 asyncio、DAG 和状态机组织审查任务。Planner 将复杂问题拆成独立调查要点，多个 Searcher 在同一层并行取证，调度过程支持并发限制、单任务超时和全局超时。Searcher 只负责查找原始条款，不生成中间结论；Refiner 是唯一生成最终结论的 Agent，直接综合全部已校验证据，减少中间结论在 Agent 之间传播造成的事实漂移。

**从粗召回到完整条款的搜索链路**

合同入库时保留全文、章节层级、页码和字符位置，并使用 bge-m3 生成向量。查询时同时执行向量检索和 BM25 检索，再通过 Reciprocal Rank Fusion 融合两路结果。Searcher 先用语义检索定位同义表达和相关条款，再用字面或正则匹配确认精确措辞、条款编号和交叉引用，最后按章节或切片读取完整原文。

搜索结果只提供短片段帮助 Agent 定位，短片段本身不会直接作为证据。所有查询都受会话和指定文档范围约束，避免不同合同之间的内容相互污染。

**基于原文的可验证证据链**

Searcher 只提交来源切片，证据内容和位置由系统从数据库中的合同全文生成。系统优先将命中切片恢复为完整章节；随后逐字符核对引用是否等于原文对应区间，并检查来源切片是否属于同一文档和章节、切片文本是否与全文一致。校验失败的候选会被直接丢弃，不进入最终报告。

每条有效证据都保存文档、章节、页码、字符范围和来源切片。Refiner 只能使用已经存在的证据编号进行引用，报告生成后还会再次审计引用编号及其原文映射，避免模型自行编造条款位置。

**共享证据索引与上下文控制**

单次研究通过共享证据索引管理所有已验证条款，并按“文档 + 字符区间”去重。不同调查任务命中同一条款时复用同一个证据编号；重复读取的章节或切片不会再次向 Searcher 注入完整正文。Searcher 之间共享证据索引，Refiner 在生成结论时读取对应完整原文，从而减少重复上下文，同时保留证据完整性。

系统同时记录规划轮次、搜索调用、证据物化、原文校验、引用有效性和 token 消耗，用于评估不同编排与检索策略。

**面向合同审查的评测体系**

评测覆盖端到端判断和证据检索两个层面：ContractNLI 用于验证系统能否基于合同原文判断支持、矛盾或无法确定；LegalBenchRAG 用于衡量 Searcher 对相关文档和标注区间的覆盖能力。除分类和检索指标外，系统还记录证据物化、原文校验和最终引用审计结果，使结论质量与证据质量能够分别分析。

## 📊 评测结果

| 评测任务 | 规模 | 核心结果 |
| --- | ---: | --- |
| **ContractNLI** | 150 条 | Accuracy **80.00%**；Weighted F1 **79.78%** |
| **LegalBenchRAG** | 100 条 | 文档级 Precision / Recall **86.39% / 86.39%**；Span Recall **75.99%** |
| **引用原文校验** | 233 条引用、200 条检索证据 | 原文校验通过率均为 **100%** |

ContractNLI 各类别 F1 为：Contradiction 72.73%、Entailment 84.35%、Neutral 76.67%。LegalBenchRAG 的 Span Precision 为 7.88%，Span F1 为 12.90%。字符级 Precision 较低，是因为系统返回完整条款，而标注答案通常只覆盖条款中的最小相关区间；完整条款扩大了证据范围，也保留了判断所需的上下文。

## 🛠️ 技术栈

| 层级 | 技术 |
| --- | --- |
| **语言与并发** | Python、asyncio |
| **Agent 编排** | DAG、状态机、Semaphore、对象池 |
| **文档与证据存储** | PostgreSQL、pgvector |
| **检索服务** | 向量检索、BM25、RRF、字面与正则匹配 |
| **嵌入模型** | bge-m3 |
| **模型接入** | OpenAI 兼容接口，支持为不同 Agent 配置不同后端 |
